# cache-basics: кеш на простых функциях

Учебный пример перед кешем справочников поверх Kafka. Kafka здесь нет: я вызываю функции кеша вручную и тестами проверяю, что он ведёт себя правильно. Цель — разобраться с базовыми вещами в Rust, на которых будет держаться настоящий сервис: словарь, блокировка, работа из нескольких потоков.

## Как запустить

```bash
cargo run    # сценарий: базовые операции + один писатель и три читателя
cargo test   # 9 тестов
```

Внешних библиотек пока что нет, нужен только установленный Rust (https://rustup.rs).

## Что есть в коде

| Функция | Что делает |
|---|---|
| `new_cache()` | создаёт пустой кеш |
| `put(cache, key, value)` | кладёт значение; если ключ был, заменяет |
| `get(cache, key)` | возвращает `Some(значение)` или `None` |
| `delete(cache, key)` | удаляет ключ; `true`, если он был |
| `len(cache)` | сколько записей |
| `apply(cache, key, value)` | как будто пришло сообщение из Kafka: `Some` → положить, `None` (tombstone) → удалить |

Что проверяют тесты:

| Тест | Правило |
|---|---|
| `empty_cache_has_nothing` | новый кеш пустой |
| `put_then_get` | что положили, то и достали |
| `last_value_wins` | новое значение по ключу заменяет старое, запись остаётся одна |
| `keys_do_not_mix` | разные ключи не мешают друг другу |
| `delete_removes_key` | после удаления ключа нет |
| `delete_missing_key_is_ok` | удалить несуществующий ключ — не ошибка |
| `tombstone_deletes` | сообщение без тела удаляет запись |
| `keys_are_case_sensitive` | `p-1` и `P-1` — разные ключи |
| `readers_never_see_old_value_after_new_one` | один пишет версии 1..1000, четверо читают параллельно; никто не видит версию «назад» |

## Что я использовала и почему

| Что | Зачем мне | Почему не другое |
|---|---|---|
| `HashMap<String, String>` | хранить «ключ → значение», искать по ключу | `BTreeMap` держит ключи отсортированными, но поиск медленнее (O(log n)), а порядок мне не нужен. `Vec` пришлось бы перебирать целиком |
| `RwLock` | один поток пишет, много читают одновременно | `Mutex` пускает только одного, даже если все только читают. Справочник читают часто, а меняют редко |
| `Arc` | чтобы кешем владели несколько потоков сразу | `Rc` делает то же самое, но не потокобезопасный, и компилятор не даст передать его в другой поток |
| `std::thread` | проверить кеш, когда к нему обращаются одновременно | async (tokio) будет в сервисе, для понимания основ обычных потоков хватает |
| `Option<String>` | ответ «значение есть / значения нет» | в Rust нет null |
| `.unwrap()` у блокировок | ошибка там возможна, только если другой поток упал внутри блокировки; для учебного примера честнее упасть | нормальная обработка ошибок — когда будет сервис |
| только стандартная библиотека | сначала понять основы | `DashMap`, `parking_lot` и т.п. — потом, для сравнения |

## Справка: как я это понимаю

### Владение и заимствование (ownership, borrowing)

У каждого значения в Rust ровно один **владелец**. Когда владелец выходит из области видимости (закрывающая `}`), значение удаляется, а память освобождается сразу. Поэтому Rust не нужен сборщик мусора: момент освобождения известен ещё при компиляции.

Значение можно **одолжить** по ссылке, не забирая его:
- `&T` — посмотреть. Таких ссылок может быть сколько угодно одновременно.
- `&mut T` — поменять. Такая ссылка может быть только одна, и пока она есть, других нет.

Это правило проверяет компилятор. Отсюда и защита от гонок данных: «двое одновременно пишут» или «один пишет, другой читает» в обычном коде просто не скомпилируются.

Источник: https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html

### `String` и `&str`

- `String` владеет своим текстом: память под буквы принадлежит ей.
- `&str` — ссылка на чужой текст, своей памяти у неё нет. `"p-1"` в коде — это `&str`.

В функции я принимаю `&str` (удобно передавать и литералы, и `String`), а в словарь кладу `String` через `.to_string()`: словарь должен сам владеть ключами и значениями, иначе они пропадут, когда закончится вызывающая функция.

Источник: https://doc.rust-lang.org/book/ch08-02-strings.html

### `Option`

Вместо null в Rust есть `Option<T>`: либо `Some(значение)`, либо `None`. Компилятор не даст использовать значение, пока не разобран случай `None`, поэтому «забыть проверить на null» нельзя. В кеше `None` из `get` будет означать 404, а `None` в `apply` — tombstone.

Источник: https://doc.rust-lang.org/std/option/

### `HashMap` — тонкости

**Как устроен.** Из ключа считается хеш (число), по нему определяется место в таблице. Поэтому поиск, вставка и удаление в среднем занимают O(1), то есть почти не зависят от числа записей. С версии Rust 1.36 внутри используется реализация hashbrown — порт SwissTable от Google.

**Хеш-функция по умолчанию — SipHash** со случайным ключом. Она чуть медленнее самых быстрых, зато защищена от HashDoS: атаки, когда злоумышленник подбирает ключи с одинаковым хешем, и словарь деградирует до перебора. Хеш-функцию можно заменить на более быструю, если ключи приходят не от внешних пользователей.

**Порядок не гарантирован.** Из-за случайного ключа хеширования порядок перебора может отличаться даже от запуска к запуску. Если понадобится отдавать список записей в одном порядке, его надо сортировать отдельно или брать `BTreeMap`.

**Требования к ключу.** Ключ должен уметь хешироваться и сравниваться: реализовать `Hash` и `Eq`. `String` это умеет. Сравнение побайтовое, поэтому ключи чувствительны к регистру (в C# я бы передала `StringComparer.OrdinalIgnoreCase`).

**Поиск по `&str` при ключах `String`.** `map.get("p-1")` работает без создания новой `String`: `String` умеет «притворяться» `&str` для поиска (типаж `Borrow`). Лишней аллокации на каждый запрос нет.

**Рост.** Когда место кончается, словарь выделяет таблицу побольше и перекладывает в неё все записи. Это редкая, но дорогая операция. Если заранее известно, сколько будет записей, можно сразу выделить место: `HashMap::with_capacity(n)`.

**Память после удаления.** `remove` не возвращает память операционной системе: таблица остаётся того же размера. Ужать её можно через `shrink_to_fit()`. Для справочника это не проблема, но для замеров памяти это стоит учитывать.

**`insert` возвращает старое значение.** `map.insert(k, v)` возвращает `Some(старое)`, если ключ был. Так можно понять, была это вставка или замена. Для сложной логики («вставить, только если…») есть `entry`.

**Чем похож на C#.** Это аналог `Dictionary<TKey, TValue>`: тоже O(1) в среднем и тоже без гарантии порядка.

Источники:
- https://doc.rust-lang.org/std/collections/struct.HashMap.html
- https://doc.rust-lang.org/std/collections/index.html — как выбирать коллекцию
- https://github.com/rust-lang/hashbrown

### `RwLock` — зачем он мне и как работает

**Проблема.** `HashMap` сам по себе нельзя менять из одного потока, пока другой из него читает: читатель может попасть на полузаписанную таблицу. В C# это была бы тихая ошибка во время работы. В Rust такой код просто не скомпилируется.

**Решение.** `RwLock` (read-write lock) — блокировка с двумя режимами:
- `read()` — «я только читаю». Читателей может быть сколько угодно одновременно.
- `write()` — «я меняю». Писатель только один, и пока он пишет, читатели ждут.

Это подходит под кеш справочников: читают много HTTP-запросов, пишет один поток, который читает Kafka.

**Блокировка снимается сама.** `read()` и `write()` возвращают «охранника» (guard). Пока охранник жив, блокировка взята. Когда переменная заканчивается, охранник удаляется, и блокировка снимается автоматически. Забыть её снять нельзя. Похоже на `using` / `lock` в C#, только работает всегда.

**Держать блокировку как можно меньше.** Поэтому в `get` я делаю копию значения (`cloned()`) и сразу отпускаю блокировку, а не возвращаю ссылку внутрь словаря. Вернуть ссылку компилятор бы и не дал: она пережила бы блокировку.

**Почему `.unwrap()`.** `read()` и `write()` возвращают `Result`. Ошибка бывает только в одном случае: какой-то поток упал с паникой, пока держал блокировку. Тогда данные внутри могут быть наполовину изменены, и блокировка считается «отравленной» (poisoning). Для учебного примера я решила, что в такой ситуации лучше упасть.

**Кого пускать первым.** В документации сказано, что это зависит от операционной системы: Rust не обещает, что писатель не будет долго ждать, если читатели идут потоком (writer starvation).

**Ловушка: дедлок в одном потоке.** Если поток держит `read()` и в это же время просит `write()` у той же блокировки, он будет ждать сам себя. Документация говорит, что так может случиться дедлок или паника. Поэтому функции у меня маленькие, и каждая берёт блокировку только один раз.

**В C#** ближайший аналог — `ReaderWriterLockSlim`.

Источники:
- https://doc.rust-lang.org/std/sync/struct.RwLock.html
- https://doc.rust-lang.org/std/sync/struct.Mutex.html#poisoning
- https://doc.rust-lang.org/book/ch16-03-shared-state.html

### `Arc` — несколько владельцев

У значения может быть только один владелец, а кеш нужен сразу нескольким потокам. `Arc` (Atomically Reference Counted) хранит данные один раз и считает, сколько у них владельцев. `Arc::clone` не копирует кеш, а только увеличивает счётчик на 1. Когда последний владелец пропадает, данные удаляются.

`Arc` даёт только **общий доступ на чтение**. Менять данные через `Arc` нельзя, поэтому внутри лежит `RwLock`: связка `Arc<RwLock<...>>` — стандартный способ «делить изменяемые данные между потоками».

Источник: https://doc.rust-lang.org/std/sync/struct.Arc.html

### Откуда «нет гонок данных»

Компилятор помечает типы двумя признаками:
- `Send` — значение можно передать в другой поток;
- `Sync` — значение можно читать из нескольких потоков по ссылке.

`Arc` и `RwLock` их имеют, `Rc` и голый `HashMap` под изменение — нет. Если попытаться поделить между потоками что-то небезопасное, будет ошибка компиляции.

**Чего Rust НЕ ловит:**
- дедлоки (например, ловушка с `read()` + `write()` выше);
- логические гонки: правильный доступ к памяти, но неправильный порядок действий. Например, в Kafka старая версия пришла позже новой. От этого защищает логика кеша, а не компилятор.

Источник: https://doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html

### Потоки: `spawn`, `move`, `join`

- `thread::spawn(...)` запускает новый поток операционной системы.
- `move` перед замыканием переносит в поток всё, чем он пользуется (у меня — свою копию `Arc`). Без `move` компилятор не пустит: поток может жить дольше функции, которая его создала.
- `join()` ждёт, пока поток закончит.

Источник: https://doc.rust-lang.org/book/ch16-01-threads.html

### Как это связано с задачей (Rust vs .NET)

- В .NET все строки и словарь кеша живут в управляемой куче. Сборщик мусора периодически их обходит, и паузы сборки бьют по самым медленным ответам (p99).
- В Rust память освобождается сразу, когда удаляется владелец (например, при `remove` или замене значения в `insert`). Пауз сборки нет, а у объектов нет служебных заголовков .NET.
- Но копирование в `get` (`cloned()`) — это выделение памяти на каждый запрос. В сервисе это стоит убрать, например хранить значения в `Arc<str>` или `Bytes`, чтобы отдавать без копирования.

## Что сознательно упрощено

- Одна блокировка на весь кеш. Пока пишущий поток обновляет один ключ, ждут читатели всех ключей.
- На каждый `get` — копия строки.
- Обычные потоки вместо async. В сервисе будет tokio. Стандартный `RwLock` там можно использовать, если не держать блокировку через `.await`.
- Нет версий записей: «последнее значение» = «последнее пришедшее». В Kafka это верно внутри одной партиции.
